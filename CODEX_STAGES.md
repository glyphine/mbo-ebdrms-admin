# E-BDRMS: staged Codex implementation prompts

Use these prompts **one stage at a time**, in order. Place `AGENTS.md` at the API repository root first. Each stage assumes the previous accepted stage has been committed. Do not blindly run commands against a database containing important records. These prompts intentionally allow Codex to inspect actual schema and versions instead of guessing.

## Stage 0 — Repository audit and implementation map (no code changes)

> Read `AGENTS.md`, `package.json`, Fastify bootstrap files, Drizzle schema/config and migrations, existing tests, `templates/*.eta`, vetted document assets, and the supplied renderer/fixture reference only. Summarize the current architecture and produce a minimal implementation map for the requested device-gated auth, RBAC, trusted document rendering, backups, and Docker Compose deployment. Identify missing DB tables/constraints and exact migration risks. Propose API endpoints and stage dependencies. Do not edit files, install packages, or touch databases. Return a concise list of decisions that materially require my approval.

## Stage 1 — Fastify foundation and API contract

> Follow `AGENTS.md`. Implement or normalize the smallest viable Fastify modular-monolith foundation using existing conventions: `app.ts`/`server.ts` separation, validated configuration, database lifecycle, unified errors, request schemas, `/api/v1` routing, `/health/live` and `/health/ready`, structured redacted logging, and OpenAPI generation if compatible with the installed stack. Do not add auth behavior or modify business tables yet. Add focused tests for startup, validation, health/readiness, and error formatting. Run typecheck and relevant tests; report what changed.

## Stage 2 — Device/session persistence and safe enrollment

> Follow `AGENTS.md` and inspect the actual Drizzle schema/migrations. Implement the minimum persistent models for user-bound devices, login sessions, and refresh-token rotation/history (reuse existing tables if appropriate). Use constraints and indexes. Build enrollment/revocation **service logic** with pending/approved/revoked states and a restricted initial-admin bootstrap plan; registration must not grant access by itself. Defer public enrollment/approval routes until authentication and RBAC guard them in Stages 3–4. Never store raw device credentials or refresh tokens. Add a reviewed non-destructive migration and tests for enrollment states and cross-user misuse. Explain the software-bound device security limit. Do not implement JWT endpoints yet.

## Stage 3 — Authentication and token lifecycle

> Follow `AGENTS.md`. Implement password verification, pending device enrollment requests after credential verification, approved-device login, **device credential proof on login and refresh**, short-lived access JWT, single-use rotating refresh tokens, logout, per-device session revocation, and middleware that rejects invalid/disabled user, device, or session state. Use atomic refresh rotation and reuse detection. Prefer opaque refresh tokens unless the repository already establishes a justified JWT refresh contract; access JWTs must validate issuer/audience/type/expiry and carry `sub`, `sid`, `did`, and `jti`. Rate-limit sensitive endpoints; redact secrets. Preserve a clear path for the React Native client to store credentials in OS secure storage. Add focused tests covering expired/replayed tokens, race conditions, revoked devices, and logout. Do not implement RBAC business endpoints in this stage.

## Stage 4 — RBAC and document-type access control

> Follow `AGENTS.md`. Implement reusable authorization guards using existing user-role, role-permission, and document-type permissions tables. Devices determine whether a session is allowed, but roles determine what it can do. Apply deny-by-default and document record-level status rules; `managingOfficeId` is metadata unless a specific office-scoping policy exists. Add authenticated administrator endpoints for pending-device approval/revocation plus narrowly scoped role/user management, with audit events for permission changes. Test denied access, revoked sessions, stale tokens, and document-type grants. Do not introduce per-device role assignments without a concrete requirement.

## Stage 5 — Trusted templates and document definitions

> Follow `AGENTS.md`. Inspect the actual schema and the supplied `index.ts` document definitions plus `templates/*.eta` files; do not assume the files exist yet. Implement a typed, server-owned registry for CAFOA, RAAOCO, RAAOFE, RAAOMOOE, RAAOPS, and SAAOB: common `DocValue`/recursive `DocField`/`DocEntry`/`PdfOptions` concepts, shared RAAO structures, nested CAFOA and SAAOB fields, print defaults, and controlled template identifiers. Define a validator for the *actual recursive shapes* (including array items, optional/null spacer rows, financial decimal strings, and bounds). Reuse the existing Drizzle document-type/template-version tables. Build template listing/retrieval and a trusted **repo-file-to-published-version** process that snapshots reviewed `.eta` source (or version-addressed immutable artifact), schema, PDF settings, and CSS/assets provenance. The publication mechanism must be limited to trusted deploy/maintenance operations, not arbitrary API-submitted Eta. Existing published versions remain immutable. Reject unknown fields, client-provided resource paths, executable markup/code inputs, and unapproved assets; allow markup-looking plain text only as safely escaped text. Add tests for every type, template drift, data validation, and historical version references. Do not generate PDFs or create a template-code editor yet.

## Stage 6 — Documents and immutable revisions

> Follow `AGENTS.md`. Implement create/read/list and revision APIs for documents, using immutable revisions tied to exact trusted template versions, `createdBy`, `managingOfficeId` metadata, and non-account signatory snapshots. Accept **structured values only**, validate against the stored recursive schema for the selected document type (CAFOA/RAAO/SAAOB), and never trust client-provided template paths, Eta source, CSS, PDF settings, computed totals, or unrestricted field keys. Define draft/finalized/archived transitions and enforce them in services. Use optimistic concurrency (expected revision/version) to prevent lost updates, and wrap revision data, typed financial projections, and audit events in transactions. Test nested values, optional/null print rows, concurrent edits, finalization, history, and user permissions. Do not overwrite finalized history or silently upgrade templates.

## Stage 7 — Secure PDF generation

> Follow `AGENTS.md`. Implement the PDF service by adapting the supplied `index.ts` **not replacing its rendering approach**: resolve the document revision and matching immutable, trusted template snapshot; transform validated values into Eta's top-level data object; embed approved logos/assets (including municipal logo) as vetted local/data URLs; call Eta to produce HTML; compile trusted Tailwind CSS using the installed `@tailwindcss/node` API and include reviewed per-form print CSS; render with Playwright Chromium respecting `PdfOptions` (A4/Letter/Legal/A3/A5 where supported, margins and RAAO landscape). Never execute client-supplied Eta, JS, raw HTML, CSS, resource names, includes, or asset URLs. Use Eta's escaped output for user text, with tests for all exceptional raw output. Disable browser-side JavaScript when compatible with required image/font readiness, block HTTP(S)/file requests, avoid any CDN dependency, bound rendering time/rows/output bytes/concurrency, and close each context/page on every path; do not unnecessarily launch a browser for each document. Test that older revisions render with their original template version after publishing a new one. Port `test_data.ts` scenarios as **test-only fixtures**, including variable CAFOA rows, four RAAO types, deeply nested SAAOB categories/totals, `null` spacer rows, printable logo, and PDF orientation. Test injection strings, blocked remote fetch, missing assets, layout/PDF output, render failures, and concurrency. Serve PDFs with correct private-download headers. Avoid a job queue unless proven necessary.

## Stage 8 — Financial Reporting Dashboard, PDF Export, and Auditing

> Follow `AGENTS.md`. Implement a server-side financial reporting API for a configurable dashboard inspired by SAAOB financial summaries, without generating or modifying official SAAOB documents. Use existing Drizzle financial records and authorized document revisions as data sources. Support filters for fiscal periods, dates, offices, and applicable expenditure categories, along with configurable financial metrics including appropriations, allotments, obligations, and balances. Provide REST endpoints returning aggregated metric values, breakdowns, and chart-ready datasets for consumption by the separate React Native client. Keep the API independent of the client's charting and UI libraries. Implement PDF snapshot export using the existing trusted Eta/Tailwind/Playwright rendering infrastructure. The exported PDF must reflect the selected filters, financial metric cards, applicable charts, report period, and a consistent snapshot of the underlying data. Use a dedicated trusted reporting template, not an official SAAOB document template. Do not accept arbitrary HTML, JavaScript, or template source from the client. Preserve exact financial precision, correct office relationships, and authoritative revision selection. Avoid double-counting aggregate rows and overlapping financial representations. Do not invent unsupported accounting calculations or infer unavailable reporting periods. Complete audit event recording and authorized retrieval with actor, target, action, and timestamp, enforcing append-only application semantics. Add appropriate RBAC checks, request validation, pagination, query limits, and justified indexes. Test filters, financial aggregation, chart datasets, PDF output consistency, revision selection, unauthorized access, and audit completeness. Use test fixtures where necessary. Do not seed production data, introduce an analytics database, implement React Native UI code, or add unrelated infrastructure.

## Stage 9 — Containerized development and production deployment

> Follow `AGENTS.md`. Add a minimal multi-stage API Dockerfile (including the Playwright Chromium/browser runtime dependencies actually used), `.dockerignore`, Docker Compose setup for API + PostgreSQL with persistent DB data, healthchecks, internal DB networking, and environment-specific configuration. Ensure the runtime image contains the reviewed `templates/*.eta`, required vetted fonts/logo/assets, and any precompiled CSS or immutable versioned template resources; test that template lookup does **not** depend on a developer-machine path or runtime CDN access. Keep native local development; pin compatible images, run non-root, and keep credentials out of git/image layers. Document reproducible build, migrations, PDF smoke test, and startup. Validate Compose and startup if tools permit. Do not deploy to a real server.

## Stage 10 — Database backups, test restores, and release rollback

> Follow `AGENTS.md`. Add scheduled PostgreSQL backups in custom format with protected storage outside the DB volume, retention, status logging, and failure reporting. Implement a **non-destructive** test restore to a throwaway database. Explicitly cover published template snapshots, trusted `templates/` releases, municipal logos/fonts, other printable assets, compiled styles when applicable, and any issued PDF artifacts stored outside PostgreSQL; a DB dump alone does not back up external files. Create deployment and application-image rollback scripts with confirmation, pre-deploy backup verification, health checks, and backward-compatible migration expectations. Test that a restored old revision can still render with its original template version/assets. Never automate DB downgrade or restore over live records. Document recovery limits and operator actions.

## Stage 11 — Acceptance and handover hardening

> Follow `AGENTS.md`. Perform a targeted end-to-end review of the API contract against the client integration needs and core E-BDRMS workflows. Add a short operator runbook and API examples: approve a device, log in, rotate tokens, create/revise CAFOA and RAAO and SAAOB, render/print a PDF, revoke a device, take/verify a backup. Include an acceptance matrix for **all six document types**, print fidelity/orientation, nested/blank rows, signatories, old revision/template reprints, denied remote assets, and Eta injection safety. Audit critical risks without broad refactors. Run available tests and report actual results/failures/blockers. Do not claim production readiness without verified restore, auth-revocation, and template-injection checks.

## How to use the prompts

- Start a new Codex instruction with the next stage verbatim, or paste the stage section.
- Review the diff and tests after every stage; commit accepted work before proceeding.
- If Codex needs to change the agreed data model or security guarantees, require it to state the trade-off before proceeding.
- Build the React Native client against the resulting OpenAPI contract in a **separate repository/stage sequence**, not in these backend stages.
